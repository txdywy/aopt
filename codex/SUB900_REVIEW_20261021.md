# Sub-900 review, 2026-10-21

**Historical review:** the following records experiments before the public
880-cycle implementation was found. The current root submission now passes
the unchanged official suite and 270 independent cases at **880 cycles**.
See [the subsequent reproduction](SUB900_BREAKTHROUGH_20261021.md).

The objective is still open. No new kernel below 900 cycles was obtained in
this review, and the practical submission remains the verified 981-cycle
`../perf_takehome.py`. The separate huge 979-cycle artifact is not an upload
recommendation.

## Public result checked

The rendered [VLIW Kernel Challenge](https://vliw-challenge.fly.dev/) scoreboard
was read with a browser, explicitly selecting **Without Indices**. Among the
100 displayed entries, 20 were below 900, and the best score was 864. Static
text retrieval omitted the score rows. This replaces the earlier uncertainty
about whether the public sub-900 results existed; it does not reproduce a
competitor's kernel. No runnable 864-cycle implementation was obtained from
the inspected public sources. No code was uploaded and no account was used.

## Current program's actual work

`resource_profile_981.json` records an execution of the current program on a
full-width seed-zero tree and batch, with final values checked against the
unchanged frozen reference:

| Engine | Executed slots |
|---|---:|
| ALU | 11471 |
| VALU | 5770 |
| LOAD | 1886 |
| FLOW | 937 |
| STORE | 62 |

Arithmetic lane work is `11471 + 8*5770 = 57631`. At 899 cycles, the optimistic
combined ALU/VALU capacity is 53940, a deficit of 3691. LOAD and FLOW exceed
their 899-cycle capacities by 88 and 38 slots respectively. These bounds are
for this program's executed work, not for other algorithms or the problem.

Removing all 1792 existing deep-address conversions for free would still
leave an arithmetic floor of 931. Address relayout therefore needs another
independent reduction and must charge its preprocessing loads and stores.
A hypothetical one-operation reduction at every hash saves 4096 lane units,
but still needs LOAD and FLOW reductions. Neither saving has been implemented.

## A new input-key absorption probe

`probe_keyed_first_mad.py` checks a family not represented by the previous
first-slice search: permit an XOR key on the first MAD's input, because an
existing node-XOR instruction could absorb that key without another opcode.

To remove C1 from `a XOR (a >> 19) XOR C1`, the first MAD would need to emit
`a XOR K`, where `K = C1 XOR (C1 >> 19) = 0xc761dad0`. The tested family is

```
A*(x XOR S)+B == (4097*x+0x7ed55d16) XOR K  (mod 2**32)
```

The unknown constants A, B, S are unrestricted. Bit lifting has no surviving
candidate at six bits. An independent exhaustive six-bit check covers all
4096 choices of A and S, with B fixed by the necessary x=0 equality, and also
finds none. Since both sides are compatible with reduction modulo 64, this
excludes the stated family at 32 bits. Full-width positive controls K=0 and
K=0x80000000 retain their known exact identities. This is not a lower bound
on arbitrary hash circuits, different encodings, or the entire kernel.

```
python3.12 -m codex.probe_keyed_first_mad
```
