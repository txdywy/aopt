## 为什么这次能突破

| 指标 | 原 981 版本 | 当前 880 版本 |
|---|---:|---:|
| ALU 指令 | 11471 | 10418 |
| VALU 指令 | 5770 | 5239 |
| 算术 lane 工作量 `ALU + 8*VALU` | 57631 | 52330 |
| LOAD 指令 | 1886 | 1724 |
| FLOW 指令 | 937 | 843 |
| STORE 指令 | 62 | 1591 |
| 完整执行周期 | 981 | 880 |

这些是两份完整程序的实际执行计数。原程序的工作量下界只约束原程序，不能作为
此题不能突破 900 的证据。新方案同时降低算术、加载和选择工作，把 STORE 用起来：

- 反向、异或编码的树记录一次存放 3 或 7 个相关节点，后续一条 vload 可以供应
  多层遍历。树的运行时内容仍由模拟指令从输入内存读取和重排。
- 第 3/14 轮的加载目标以步长 2 交错，保留每个 walker 的两个孩子；两条 vselect
  可完成八个 walker 的选择，减少独立选择和重新打包。
- 部分选择改为先写默认值，再按条件向临时 bank 写候选值，最后一次 vload 取回。
  未选中的写入送到不再使用的头部位置。头部、树、初始 indices 的已消费空间
  因而可以充当临时存储；本赛道只检查最终 values。
- 哈希仍利用乘加等式和延迟最终 XOR；本次突破并不依赖未经验证的新哈希恒等式。

对于当前固定的引擎分配，5239 条 VALU 指令已经需要至少 `ceil(5239/6)=874`
周期。这只是不计依赖和启动开销的容量下界，也只约束这组指令；不能推出全局最优。

## 其他公开情报

[Josu San Martin 公开的研究日志](https://github.com/josusanmartin/josusanmartin.github.io/blob/master/vliw/chat.log)
记录了 864 周期、1532 scratch、约 0.5 MB JSON 的结果，以及其测试报告。
本次未取得对应完整内核，所以 **864 仍是公开日志中的成绩，不是本地复现成绩**。

日志给出的后续方向包括：双线性树记录地址、利用带符号 parity 在 MAD 中折叠
路径地址、步长 4 的深层记录，以及重叠加载后的双 vselect 选择。中间记录携带的
anchor 和已消费输入区的复用有严格先后依赖，不能仅凭地址空间能放下就安全替换。
