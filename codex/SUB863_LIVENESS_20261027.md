# 863 继续探索：逐车道活跃性与 d9/d10 替代方案（2026-10-27）

**可执行最好成绩仍为 864 cycles，本轮没有得到 863 程序。**

## 1. 逐车道活跃性普查

此前的值级普查只找“重复值”，没有检查“写出后从未被读”的车道。本轮在冻结
模拟器上逐周期记录每条指令每个车道的读写，再从最终输出区
`mem[2310:2566]` 反向做活跃性分析：

- 标量 `load`/`vload` 按本次运行的实际地址读内存；`store`/`vstore` 按实际地址写；
- vselect 保守地视为三个输入都被读（结果车道活跃时）；
- 三个随机种子（11、22、33）取并集。

| 引擎 | 结果 |
|---|---|
| ALU | 10,321 条全部活跃，0 条死指令 |
| VALU | 5,168 条全部 8 车道活跃 |
| FLOW | 579 条 8/8，252 条 4/8（子节点半选择），2 条 5/8，18 条 add_imm |
| LOAD | 147 条 8/8；记录 gather 768 条 3/8、256 条 4/8（带锚点）；d9 gather 256 条 1/8；标量 260 条 |

单个种子会显示少量“死”ALU 指令（种子 5 有 45 条），它们构造的是本次输入
没有访问到的节点记录字段；换一组输入就会被读到，所以必须按并集判断。
算术部分没有任何可删除或可从 VALU 收窄为 ALU 的车道。连同此前的重复值普查
（只有 4 次重读和 `x|0` 窗口复制），864 程序在“死代码”“重复计算”“部分车道”
三个意义上都没有冗余。LOAD 的字利用率很低（d9 每次 vload 只用 1 个字），但
受选择车道引理和指针成本限制，这些空字无法放入有用数据（见第 2 节）。

## 2. d9/d10 的替代方案

现行 d9、d10 每元素 4 条运算：两个地址、两次 C5 恢复；每组另有 3 条 FLOW、
16 次 LOAD。逐项核算三种替代：

| 方案 | 每元素运算 | 额外代价 |
|---|---:|---|
| d8 两层记录装 C5 预异或的 d9 子节点对 `[L9', R9']` | 4（d8 地址 1、d10 地址 2、d10 恢复 1） | d9 节点就地预异或 512 lane，另需 64 个新块指针，合计 +576 |
| 原始树相邻子节点对 gather（d9 对、d10 对） | 5 | 每组 FLOW 3 → 5 |
| d9、d10 交错布局，让 d9 窗口含子节点 | 4 | 只能按 2/4/8 字块搬运，每个单元一次 vstore 需 256 个指针，并多 192 次 LOAD |

d10 地址在任何方案里都要合入与 i9 成线性的值和 `b9`：若 d9 不 gather，
就要从 d8 的值再合入 `b8`、`b9` 两个位，多一条运算。与现行相比都没有净省。

## 3. 本轮其他核对

- **节点选择不提取奇偶位。** vselect 只看“非零”；乘加只有乘数为 `2^31` 时结果
  才只依赖第 0 位，但那会把选择放进第 31 位，地址无效。`<`、`==`、`//`、`%`、
  变量移位都不能一次给出“地址 + 奇偶位”。
- **把节点异或并入选择。** 先对两个候选各做异或再选择要两条运算；用乘法实现
  条件异或也至少两条。
- **用尾部空闲的 LOAD/FLOW。** 第 842 周期后的 LOAD 只能服务后续依赖 ≤21 周期的
  读取；能放进去的只有末轮子节点改由 gather 取，但每组要多一条地址运算。

## 4. 结论

864 程序没有死车道、没有重复计算、没有部分车道浪费；d9/d10 的结构替代都没有
净省。仍然需要每元素每轮层面的新原语。

复现：

```bash
python3.12 codex/liveness864.py 11 22 33
```
